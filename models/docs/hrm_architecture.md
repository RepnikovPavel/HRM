# HRM (Hierarchical Reasoning Model) на задаче Sudoku — полное описание

Документ описывает модель HRM так, как она реализована в этом репозитории и
применяется к задаче Sudoku-Extreme: архитектуру, обучение, инференс,
вычислительный бюджет и мотивацию подхода. Каждое утверждение сверено либо с
исходным кодом (`models/hrm/hrm_act_v1.py`, `models/layers.py`,
`models/losses.py`, `models/sparse_embedding.py`, `pretrain.py`,
`evaluate.py`, `dataset/build_sudoku_dataset.py`), либо с текстом статьи
(`paper/document.md`, arXiv:2506.21734v3). Все обозначения вводятся явно.

## 0. Зачем изучать эту модель

Коротко о мотивации, потому что без неё дальнейшие детали выглядят как набор
случайных трюков.

1. **Задача, недоступная трансформерам «в лоб».** Sudoku-Extreme — это судоку,
   требующие в среднем 22 ветвления с возвратом (backtracking) у
   специализированного солвера tdoku (статья, §3.1). Обычный трансформер той
   же ширины и с тем же числом параметров, обученный предсказывать ответ
   напрямую («Direct pred»), набирает 0% точности на 1000 примерах и лишь
   16.9% даже на полном датасете из 3.8M примеров (статья, §3.2, Figure 2).
   CoT-модели (o3-mini-high, Claude 3.7 и т.п.) набирают 0%. HRM с 27M
   параметров решает задачу почти идеально при обучении на полном датасете и
   радикально лучше всех базовых линий при обучении всего на 1000 примерах,
   с нуля, без предобучения и без цепочек рассуждений.

2. **Глубина через рекуррентность, а не через слои.** Фиксированная глубина
   трансформера ограничивает его классами сложности $AC^0$/$TC^0$ (статья,
   §1): за один проход он не может выполнить сколь угодно длинный поиск.
   HRM получает «эффективную глубину» в сотни слоёв, многократно прогоняя
   одни и те же 8 слоёв, не увеличивая число параметров.

3. **Обучение без BPTT.** Рекуррентные сети обычно учат через
   backpropagation through time с памятью $O(T)$ и плохой утилизацией GPU.
   HRM использует one-step gradient approximation (обоснование через Deep
   Equilibrium Models), память по времени $O(1)$, backward идёт только через
   последнюю пару проходов. Это делает обучение дешёвым и простым для
   оптимизации на уровне CUDA-ядер (чем и занимается `hrmfast/` в этом
   репозитории).

4. **Адаптивное время вычисления.** Модель сама решает, сколько «думать» над
   примером (механизм ACT на Q-learning), а на инференсе точность можно
   поднять, просто увеличив лимит шагов, без переобучения (статья, Figure 5c).

5. **Практическая ценность для этого репозитория.** Модель маленькая (27M
   параметров), код компактный (~300 строк ядра), задача синтетическая и
   бесконечно генерируемая. Это идеальный полигон для исследования
   рекуррентного reasoning: всё измеримо, всё воспроизводимо, цикл
   «идея → эксперимент» короткий.

## 1. Задача и данные

### 1.1 Правила и формат примера

Судоку — сетка $9\times9$; каждая строка, столбец и блок $3\times3$ обязаны
содержать цифры 1..9 ровно по разу. Пример = пара (головоломка, решение),
каждая — строка из 81 символа. В исходном CSV пустые клетки — `'.'`.

Кодирование (`dataset/build_sudoku_dataset.py`):

- вход `inputs`: `'.'` → 0 (blank), цифры 1..9 → 1..9, затем **весь массив
  сдвигается на +1**, чтобы освободить id 0 под padding: blank=1, цифра $d$
  → $d+1$;
- выход `labels`: полное решение (все 81 клетка), тоже +1, т.е. значения
  2..10;
- итоговый словарь: $V = 11$ токенов: 0 = PAD (id паддинга, он же
  `ignore_label_id`, в sudoku не встречается), 1 = blank, 2..10 = цифры
  1..9 (`vocab_size = 10 + 1` в `build_sudoku_dataset.py`).

Модель должна предсказать **все 81 клетку сразу**, включая те, что были даны
во входе. Ответ считается верным только при точном совпадении всей сетки с
единственному решению (метрика `exact_accuracy`, см. §8).

### 1.2 Датасеты

Из статьи (§3.1) и `build_sudoku_dataset.py`:

- **Sudoku-Extreme-Full**: 3 831 994 обучающих примера (лёгкие из
  Kaggle/17-clue + сложные Magictour 1465, Forum-Hard, Forum-Extreme),
  строгий сплит 90/10 без эквивалентных трансформаций между train и test;
- **Sudoku-Extreme**: субсэмпл на 1000 обучающих примеров (режим
  small-sample из Figure 1 статьи; `--subsample_size 1000`);
- аугментация train (`shuffle_sudoku`, `num_aug`): случайная перестановка
  цифр 1..9, транспонирование, перестановки бэндов/стеков и строк/столбцов
  внутри них — всё это сохраняет корректность судоку;
- сложность измеряется числом backtracks солвера tdoku: среднее по
  Sudoku-Extreme = 22 (для сравнения, подборка Sudoku-Bench — 0.45);
  фильтр `--min_difficulty` отсекает слишком простые головоломки.

### 1.3 Идентификаторы пазлов

Для Sudoku `num_puzzle_identifiers = 1`, `blank_identifier_id = 0`: у всех
примеров один и тот же puzzle_id. То есть «puzzle embedding» здесь вырождается
в **один обучаемый вектор-префикс**, общий для всего датасета (в ARC, где
пазлов много, это полноценная таблица эмбеддингов; см. §4.1). Это важно для
понимания кода: механизм общий, но на Sudoku его параметрический объём —
512 чисел.

## 3. Общая схема

Статья (§2) описывает модель четырьмя обучаемыми компонентами:

- $f_I$ — входная сеть (embedding): $x \mapsto \tilde x$; в коде это
  `_input_embeddings`, результат мы обозначаем $e$;
- $f_L$ — low-level рекуррентный модуль ($L$): 4 трансформерных слоя;
- $f_H$ — high-level рекуррентный модуль ($H$): 4 трансформерных слоя той же
  архитектуры;
- $f_O$ — выходная сеть: `lm_head` (логиты токенов) + `q_head` (логиты ACT).

Поток данных за один сегмент:

```
inputs (81 токена) ──► f_I ──► e ──────────────────────────┐
                                                           ▼
        z_L ◄── L_level(z_L, z_H + e)   ← повторяется (T шагов × N_cyc циклов)
        z_H ◄── H_level(z_H, z_L)       ← 1 раз в конце каждого цикла
                                                           │
        z_H ──► lm_head ──► ŷ (81×11)                      │
        z_H[:,0] ──► q_head ──► (q_halt, q_continue)       │
                                                           │
        (z_H, z_L) ──detach──► carry следующего сегмента ──┘
```

Два состояния $z_L$ и $z_H$ живут **между** сегментами (и между optimizer
steps) в структуре `carry` — в этом суть deep supervision (§7).

## 4. Компоненты подробно

### 4.1 Входной embedding ($f_I$)

`_input_embeddings` (`hrm_act_v1.py:160`):

1. Токен-эмбеддинг: `CastedEmbedding` — таблица $E \in \mathbb{R}^{11 \times 512}$,
   инициализация truncated normal со std $= 1/\sqrt{D}$ (LeCun-подобная;
   самописный `trunc_normal_init_` в `models/common.py`, который, в отличие от
   `nn.init.trunc_normal_`, корректно пересчитывает std после усечения).
2. Puzzle-эмбеддинг $E_{pz}$ (`CastedSparseEmbedding`, `sparse_embedding.py`):
   вектор на puzzle_id, **инициализируется нулём** (`init_std=0`).
   Дополняется нулями до кратности $D$ и встаёт **первым токеном**
   последовательности. На Sudoku это одна строка из 512 нулей на старте.
   Хранится в bf16-буфере, обновляется отдельным sparse-оптимизатором
   (SignSGD, §9), потому что градиент приходит только на строки текущего
   батча — обычный Adam по разреженному градиенту вырождается в SignSGD
   (комментарий в коде).
3. Масштабирование: весь эмбеддинг умножается на $\sqrt{D} = \sqrt{512}$:

$$
e = \sqrt{D}\cdot \mathrm{Cat}\big[\,E_{pz}[\mathrm{pz}],\; E[x]\,\big]
\in \mathbb{R}^{N \times 82 \times 512}.
$$

Позиционных эмбеддингов здесь нет: позиция кодируется через RoPE внутри
attention (конфиг `pos_encodings: rope`).

### 4.2 RMSNorm

`rms_norm` (`layers.py:184`): без обучаемых gain/bias, считается в float32,
результат возвращается в исходный dtype:

$$
\mathrm{rms}(x) = \frac{x}{\sqrt{\frac{1}{D}\sum_{i=1}^{D} x_i^2 + \varepsilon}},
\qquad \varepsilon = 10^{-5}.
$$

Блоки **post-norm**: норма стоит после residual-сложения,
$h \leftarrow \mathrm{RMSNorm}(h + \mathrm{sublayer}(h))$. Это отличается от
мейнстримных pre-norm LLM и сделано намеренно: статья (§2, «Stability of
Q-learning in ACT») ссылается на теоретический результат, что post-norm +
нормировка + weight decay дают ограниченность весов и сходимость Q-learning
без replay buffer и target network.

### 4.3 Блок трансформера (`HierarchicalReasoningModel_ACTV1Block`)

Один слой, оба модуля $L$ и $H$ состоят из четырёх таких (`hrm_act_v1.py:60`):

$$
h \leftarrow \mathrm{RMSNorm}\big(h + \mathrm{Attn}(h)\big), \qquad
h \leftarrow \mathrm{RMSNorm}\big(h + \mathrm{SwiGLU}(h)\big).
$$

**Attention** (`layers.py:108`): некаузальный (все 82 токена видят друг
друга — это encoder, не языковая модель), multi-head, без bias:

$$
\mathrm{Attn}(h) = W_O \cdot \mathrm{concat}_{heads}\Big[
\mathrm{softmax}\Big(\frac{\mathrm{RoPE}(Q)\,\mathrm{RoPE}(K)^{\top}}{\sqrt{64}}\Big) V\Big],
$$

где $[Q,K,V] = W_{qkv}\,h$, $W_{qkv} \in \mathbb{R}^{1536 \times 512}$
(8 голов × 64 для каждой из Q, K, V).

**RoPE** (`layers.py:90`): поворот пар координат q и k на угол, зависящий от
позиции $p$: частоты $\theta_i = 10000^{-2i/64}$, таблицы
$\cos,\sin \in \mathbb{R}^{82 \times 64}$ предвычислены один раз.
Код использует перестановку `cat(freqs, freqs)` вместо чередования —
комментарий в коде: «Different from paper, but it uses a different permutation
in order to obtain the same calculation».

**SwiGLU** (`layers.py:164`):

$$
\mathrm{SwiGLU}(h) = W_{down}\big(\mathrm{silu}(W_{gate} h) \odot (W_{up} h)\big),
$$

$W_{gate}, W_{up}$ объединены в `gate_up_proj` $\in \mathbb{R}^{3072 \times 512}$.
Внутренняя размерность $I$ вычисляется как
$\mathrm{round}(expansion \cdot D \cdot 2/3)$, округлённая вверх до кратности
256: $\mathrm{round}(4 \cdot 512 \cdot 2/3) = 1365 \to I = 1536$. Формула
«$expansion \cdot 2/3$» — стандартный трюк GLU-вариантов: за счёт двух
матриц (gate и up) итоговое число параметров MLP соответствует обычному MLP с
расширением 4.

На GPU + bf16 блок идёт по fused-пути (`LinearResidRmsNorm` из `hrmfast`):
GEMM проекции + residual add + RMSNorm слиты в одно ядро; математика та же.

### 4.4 Головы выхода ($f_O$)

- `lm_head`: $W \in \mathbb{R}^{11 \times 512}$, без bias; применяется к
  $z_H$ и **отрезает первый токен** (puzzle-позицию):
  `output = lm_head(z_H)[:, 1:]` → $\hat y \in \mathbb{R}^{N \times 81 \times 11}$.
- `q_head`: $W \in \mathbb{R}^{2 \times 512}$ с bias; применяется только к
  первому токену $z_H[:, 0]$ (той самой puzzle-позиции, которая через
  attention «видела» всю доску) и выдаёт два логита: $q_{halt}$ и $q_{cont}$.
  Инициализация специальная (`hrm_act_v1.py:156`): веса = 0, bias = −5, т.е.
  на старте $\sigma(q) \approx 0.0067$ для обоих действий — модель почти
  никогда не останавливается раньше времени и учит сначала решатель, а потом
  уже «термостат».

Обе головы — `CastedLinear`: веса хранятся в float32, в forward приводятся к
dtype входа (bf16). Инициализация — truncated LeCun normal,
std $= 1/\sqrt{fan\_in}$.

### 4.5 Начальные состояния $z_L^0$, $z_H^0$

`H_init`, `L_init` (`hrm_act_v1.py:151`): векторы из $\mathbb{R}^{512}$,
truncated normal(std=1, усечение ±2), хранятся как persistent-буферы (едут в
чекпоинт, но не обучаются градиентом). При старте примера состояние
$(z_L, z_H)$ каждого токена инициализируется этим **одним и тем же** вектором
(растиражированным на 82 позиции); различие позиций дальше создаётся входом
$e$ и RoPE.

## 5. Ядро: двухуровневая рекуррентность

### 5.1 Что такое $L$ и $H$

Это два **отдельных набора весов** одинаковой архитектуры (по 4 блока из §4.3
каждый). Они отличаются не строением, а ролью в динамике:

- **$L$ (low-level, быстрый)** — делает детальную работу: итеративно
  уточняет состояние доски, пока «план» $z_H$ заморожен. Получает на вход
  своё прошлое состояние, состояние $H$ и (единственное место!) сам вход $e$.
- **$H$ (high-level, медленный)** — обновляется раз в цикл, глядя только на
  итог работы $L$. Держит «абстрактный план»; его обновление «перезапускает»
  под-вычисление $L$ в новом контексте.

Статья (§2, «Hierarchical convergence») объясняет, зачем это нужно: обычная
RNN быстро сходится к неподвижной точке, шаги обновления затухают, и
эффективная глубина перестаёт расти. Здесь $L$ сходится к *локальному*
равновесию, зависящему от текущего $z_H$; затем $H$ сдвигает контекст, и $L$
начинает новую фазу сходимости. Внешне это видно по «forward residual»
(норме изменения состояния): у HRM он остаётся высоким десятки шагов, у RNN
падает к нулю (статья, Figure 3).

### 5.2 Один сегмент, точно по коду (`_Inner.forward`, `hrm_act_v1.py:194`)

При `H_cycles=2`, `L_cycles=2`:

```python
with torch.no_grad():                    # фаза A: без градиента
    z_H, z_L = carry.z_H, carry.z_L
    for _H_step in range(2):             # циклы H
        for _L_step in range(2):         # шаги L внутри цикла
            if not (последний _H_step и последний _L_step):
                z_L = L_level(z_L, z_H + e)
        if _H_step != последний:
            z_H = H_level(z_H, z_L)

# фаза B: с градиентом
z_L = L_level(z_L, z_H + e)
z_H = H_level(z_H, z_L)
```

Развёртка по шагам:

| Шаг | Действие | Градиент |
|---|---|---|
| 1 | $z_L \leftarrow L(z_L,\; z_H + e)$ | нет |
| 2 | $z_L \leftarrow L(z_L,\; z_H + e)$ | нет |
| 3 | $z_H \leftarrow H(z_H,\; z_L)$ | нет |
| 4 | $z_L \leftarrow L(z_L,\; z_H + e)$ | нет |
| 5 | $z_L \leftarrow L(z_L,\; z_H + e)$ | **да** |
| 6 | $z_H \leftarrow H(z_H,\; z_L)$ | **да** |

Условия `if not (...)` в no-grad фазе просто пропускают последнюю пару
обновлений, чтобы она выполнилась уже с градиентом. Итого за сегмент:
4 прохода $L$ (16 блоков) + 2 прохода $H$ (8 блоков) = **24 исполнения блока**
при всего 8 уникальных слоях. За полный инференс из $M_{max}=16$ сегментов —
до **384 исполнений блока** на один пример: это и есть «эффективная глубина».

Обратите внимание на input injection: $e$ прибавляется к $z_H$ **только** во
входе $L$ (`z_L + (z_H + e)` через механизм `input_injection` —
`ReasoningModule.forward` складывает аргументы поэлементно). $H$ вход $e$
никогда не видит напрямую — только через $z_L$. В статье это соответствует
уравнениям $z_L^i = f_L(z_L^{i-1}, z_H^{i-1}, \tilde x)$,
$z_H^i = f_H(z_H^{i-1}, z_L^{i-1})$.

## 6. Обучение без BPTT: one-step gradient

Проблема: сквозь 24 исполнения блока за сегмент и 16 сегментов невозможно
развернуть обычный backprop — память $O(T)$ по числу шагов, батч пришлось бы
урезать.

Решение из статьи (§2, «Approximate gradient»): если рекуррентная динамика
сходится к неподвижной точке $z^*$, градиент по параметрам можно выразить
через теорему о неявной функции (аппарат Deep Equilibrium Models):

$$
\frac{\partial z_H^*}{\partial \theta}
= \big(I - J_{\mathcal F}\big)^{-1} \frac{\partial \mathcal F}{\partial \theta},
$$

где $J_{\mathcal F}$ — якобиан отображения одного цикла по $z_H$. Разложение
Неймана $(I - J)^{-1} = I + J + J^2 + \dots$ обрывается на первом члене:
$(I - J)^{-1} \approx I$. Это и есть **1-step gradient**: градиент считается
так, будто все состояния, кроме последнего, — константы.

В коде это реализовано предельно прямо:

1. фаза A сегмента — под `torch.no_grad()` (шаги 1–4 таблицы §5.2);
2. фаза B (шаги 5–6) — обычный autograd;
3. состояние на выходе отсоединяется: `new_carry = Carry(z_H.detach(), z_L.detach())`.

Путь градиента: lm_head/q_head → финальный $z_H$ → финальный $z_L$ →
эмбеддинг входа. Память не зависит от числа шагов: $O(1)$ по времени
развёртки. Цена — градиент приближённый; статья ссылается на эмпирику DEQ,
что этой аппроксимации достаточно, а «deep supervision» (ниже) компенсирует
её грубость частыми сигналами обучения.

## 7. Deep supervision и ACT: цикл сегментов

### 7.1 Carry и сегменты

Между optimizer steps пример живёт в структуре `carry`
(`HierarchicalReasoningModel_ACTV1Carry`): состояния $(z_H, z_L)$, счётчик
сегментов `steps`, флаг `halted` и копия данных примера `current_data`.

Один вызов внешней обёртки `HierarchicalReasoningModel_ACTV1.forward`
(`hrm_act_v1.py:254`) = один сегмент для всего батча:

1. Для примеров с флагом `halted` состояние сбрасывается в $(H_{init}, L_{init})$
   (`reset_carry` через `torch.where`), счётчик обнуляется, а данные
   подменяются **свежим примером из даталоадера** — так батч всегда полный,
   и GPU не простаивает на уже решённых задачах.
2. Прогоняется inner-сегмент (§5.2) → новые $(z_H, z_L)$, логиты $\hat y$,
   пара $(q_{halt}, q_{cont})$.
3. Обновляется halting-логика (§7.2) и считается target для Q-learning
   (§7.3).

Каждый сегмент даёт свой лосс и свой optimizer step (статья называет это
*deep supervision*): модель получает обучающий сигнал на каждом «витке
размышления», а не только в конце. Так как состояние между сегментами
отсоединено (`detach`), градиенты не текут сквозь сегменты — это вторая,
внешняя петля 1-step approximation.

### 7.2 Когда остановиться (только при обучении)

После сегмента $m$ (`steps = m`):

$$
\text{halt} = \big(m \ge M_{max}\big) \;\lor\;
\Big( (q_{halt} > q_{cont}) \;\land\; \big(m \ge M_{min}\big) \Big),
$$

где $M_{max} = 16$, а $M_{min}$ — случайная величина: с вероятностью
$\varepsilon_{expl} = 0.1$ сэмплируется равномерно из $\{2, \dots, 16\}$
(заставляет модель иногда «думать дольше», иначе Q-функция никогда не увидит
длинных траекторий), иначе $M_{min} = 1$. Код — `hrm_act_v1.py:274-287`.

При **оценке** (model.eval) условие с Q-головой отключено: все примеры
всегда исполняют ровно $M_{max}$ сегментов. Комментарий в коде объясняет
почему: чтобы у всех примеров батча было одинаковое число шагов — иначе
батчевание и сравнение метрик между чекпоинтами ломались бы.

### 7.3 Q-learning для головы остановки

Формализация из статьи: эпизодический MDP, состояние — $(z_H, z_L)$ после
сегмента, действия {halt, continue}; halt завершает эпизод с наградой
$\mathbb{1}[\hat y = y]$ (всё решение верно), continue даёт награду 0 и
переводит в следующий сегмент.

Таргеты (`hrm_act_v1.py:293-295`):

$$
\hat G_{halt} = \mathbb{1}[\hat y = y], \qquad
\hat G_{cont} = \begin{cases}
\sigma(q'_{halt}), & m \ge M_{max} \text{ (последний сегмент)},\\
\max\big(\sigma(q'_{halt}), \sigma(q'_{cont})\big), & \text{иначе},
\end{cases}
$$

где $(q'_{halt}, q'_{cont})$ — выход Q-головы **следующего** сегмента,
полученный вторым вызовом inner под `no_grad` (ещё 24 исполнения блока за
шаг обучения — см. бюджет §11).

Заметные инженерные решения:

- нет replay buffer и нет target network — вместо этого огромный батч
  (тысячи «параллельных сред»), как в PQN (ссылка в комментарии кода);
- стабильность deep Q-learning обеспечивается post-norm архитектурой,
  AdamW-ограниченностью весов и weight decay (статья, «Stability of
  Q-learning in ACT»);
- `target_q_continue` считается в сигмоидах и сравнивается с логитом через
  BCE-with-logits — численно это корректный кросс-энтропийный таргет.

## 8. Функция потерь и метрики

`ACTLossHead` (`models/losses.py:40`):

$$
\mathcal L = \underbrace{\mathrm{CE}_{stablemax}(\hat y, y)}_{\text{решатель}}
+ 0.5\Big(
\underbrace{\mathrm{BCE}(q_{halt}, \mathbb{1}[\hat y = y])}_{\text{цена остановки}}
+ \underbrace{\mathrm{BCE}(q_{cont}, \hat G_{cont})}_{\text{цена продолжения}}
\Big).
$$

**Stablemax** вместо softmax (`loss_type: stablemax_cross_entropy` в конфиге;
статья §2: на малой выборке stablemax обобщает лучше):

$$
s(x) = \begin{cases} x + 1, & x \ge 0,\\[2pt] \dfrac{1}{1 - x + \varepsilon}, & x < 0, \end{cases}
\qquad
\log p_i = \log \frac{s(x_i)}{\sum_j s(x_j)}.
$$

В отличие от $\exp$, функция $s$ растёт линейно и не взрывается на больших
логитах; сумма в знаменателе не уходит в overflow. Считается в float64.
Для sudoku-full в README упоминается вариант с обычным softmax CE.

Детали нормировки: лосс решателя делится на число не-паддинговых меток
примера (`loss_divisor`), для Sudoku это всегда 81; все лоссы суммируются по
батчу (`reduction="sum"`), деление на размер батча происходит снаружи.

Метрики (считаются только по примерам, которые остановились на этом шаге):
`accuracy` — доля верных клеток; `exact_accuracy` — доля полностью решённых
судоку (главная метрика); `q_halt_accuracy` — совпал ли знак $q_{halt}$ с
фактом решения; `steps` — среднее число сегментов.

## 9. Оптимизация

Два оптимизатора (`pretrain.py:141-166`):

1. `CastedSparseEmbeddingSignSGD_Distributed` для puzzle-эмбеддингов:
   lr $=10^{-2}$, weight decay 0.1. Собирает разреженные градиенты со всех
   рангов (all-gather), складывает по одинаковым id, делает шаг по **знаку**
   градиента с decoupled weight decay. Adam на разреженном градиенте ≈
   SignSGD — отсюда выбор.
2. `AdamATan2` для всех остальных весов (статья: «Adam-atan2,
   a scale-invariant variant of Adam»): lr $=10^{-4}$,
   $\beta = (0.9, 0.95)$, weight decay 0.1.

Расписание lr: косинус с линейным warmup 2000 шагов, но
`lr_min_ratio = 1.0`, т.е. после warmup lr фактически константный (статья:
«constant learning rate with linear warm-up»).

## 10. Инференс: пошагово

`evaluate.py` → `evaluate()` в `pretrain.py:311`:

1. Модель в `eval()`-режиме, `torch.inference_mode()`.
2. Для каждого батча создаётся `initial_carry`: `halted = True` у всех —
   значит, первый же сегмент сбросит состояния в $(H_{init}, L_{init})$ и
   загрузит данные батча.
3. Цикл сегментов: `carry, _, metrics, preds, all_finish = model(carry, batch)`,
   пока `all_finish = carry.halted.all()`. Поскольку в eval Q-условие
   отключено, это всегда ровно $M_{max} = 16$ сегментов, т.е.
   $16 \times 24 = 384$ исполнений блока.
4. Ответ — логиты **последнего** сегмента: $\arg\max$ по 11 токенам для
   каждой из 81 клетки. Метрики (`accuracy`, `exact_accuracy`, …) считаются
   на этом же последнем сегменте.
5. Если задан `checkpoint_path`, в `step_<k>_all_preds.<rank>`
   сохраняются `inputs`, `labels`, `puzzle_identifiers`, `logits`,
   `q_halt_logits`, `q_continue_logits` — этого достаточно для оффлайн
   анализа и визуализации (`puzzle_visualizer.html`, `arc_eval.ipynb`).

**Inference-time scaling** (статья, §2, Figure 5c): лимит $M_{max}$ на
инференсе можно поднять выше тренировочного — модель, обученная с
$M_{max}=8$, продолжает расти в точности при $M_{max}=16$ на инференсе, без
дообучения. Это свойство «думай дольше → решай лучше» — одно из главных
практических преимуществ архитектуры.

**Что модель делает внутри** (статья, §3.3, Figure 7): если декодировать
промежуточные состояния ($f_O(f_H(z_H^i, z_L^i))$ на каждом шаге), на Sudoku
траектория похожа на depth-first search с возвратами: модель заполняет клетки
гипотезами, при заходе в тупик (красные клетки-нарушения) откатывается и
пробует другую ветку.

## 11. Вычислительный бюджет

### 11.1 FLOPs одного блока (на токен)

Умножение матриц: $2 \cdot in \cdot out$ FLOPs на токен.

| Операция | in | Вес | out | FLOPs/token |
|---|---|---|---|---|
| qkv_proj | $N{\times}S{\times}512$ | $1536{\times}512$ | $N{\times}S{\times}1536$ | 1.57M |
| RoPE(q,k) | $N{\times}S{\times}8{\times}64$ ×2 | — | — | ~0.25M |
| softmax($QK^\top/\sqrt{64}$)$V$ | $N{\times}8{\times}82{\times}64$ | — | $N{\times}S{\times}512$ | 0.17M |
| o_proj | $N{\times}S{\times}512$ | $512{\times}512$ | $N{\times}S{\times}512$ | 0.52M |
| gate_up_proj | $N{\times}S{\times}512$ | $3072{\times}512$ | $N{\times}S{\times}3072$ | 3.15M |
| down_proj | $N{\times}S{\times}1536$ | $512{\times}1536$ | $N{\times}S{\times}512$ | 1.57M |
| **Блок итого** | | | | **6.98M** |

За inner-сегмент: 24 блока × 6.98M ≈ **167.6 MFLOP/token** + головы.

### 11.2 FLOPs на optimizer step

Backward идёт только по grad-фазе (8 блоков); для линейных слоёв
bwd = dx + dW ≈ 2× forward:

| Фаза | Блоков (экв. fwd) | TFLOP (N=1088, S=82) |
|---|---|---|
| fwd main (no-grad 16 + grad 8) | 24 | 14.9 |
| fwd target-Q (весь сегмент, no-grad) | 24 | 14.9 |
| bwd (8 блоков × 2×fwd) | 16 | 10.0 |
| **Итого** | **64** | **39.9** |

$$
(24 + 24) + 2\cdot 8 = 64 \text{ блока}
\;\Rightarrow\; 64 \times 6.98\text{M} \times 1088 \times 82 \approx
39.9\ \text{TFLOP/step/GPU}.
$$

Замеры на 2× RTX 5060 Ti (потолок mma.sync 52.6 TFLOPS/GPU по
`hrmfast/tests/bench_mma_peak.cu`):

| Реализация | Время шага | Эффективность GEMM-части |
|---|---|---|
| author (cuBLAS/SDPA) | 1.28 с @ gbs 2176 | 64% |
| hrmfast (наши mma-ядра) | 1.25 с @ gbs 2176 | 65% |

Остаток до 100% — не-GEMM работа (RMSNorm, softmax, RoPE, elementwise,
оптимизатор), не ложащаяся на tensor pipes; сама GEMM-часть работает на ~92%
от потолка.

## 12. Преимущества подхода и честные ограничения

Преимущества (каждое подтверждено либо статьёй, либо кодом/замерами):

1. **Эффективная глубина без роста параметров**: 8 уникальных слоёв → до 384
   исполнений блока за инференс; решает задачи, где трансформер той же
   ёмкости берёт 0%.
2. **Данные**: 1000 примеров, без предобучения, без CoT-разметки; аугментация
   — только симметрии судоку.
3. **Память обучения $O(1)$ по глубине развёртки**: нет BPTT, backward через
   одну пару проходов; батч можно раздувать до предела памяти GPU.
4. **Адаптивные вычисления**: ACT экономит шаги на простых примерах; на
   инференсе точность масштабируется лимитом $M_{max}$ без переобучения.
5. **Интерпретируемость процесса**: промежуточные состояния декодируются в
   доски — видно стратегию поиска (DFS с backtracking на Sudoku).
6. **Инженерная простота**: ~300 строк ядра, bf16, нет KV-cache, нет
   авторегрессии — весь ответ за один сегмент; прямая цель для CUDA-
   оптимизаций (hrmfast).

Ограничения, которые нужно держать в голове:

1. **Фиксированный формат**: модель — seq2seq-классификатор клеток, а не
   генеративная языковая модель; перенос на другую задачу = новая разметка
   токенов и обучение с нуля.
2. **1-step gradient — приближение**: оно работает постольку, поскольку
   динамика близка к сходимости; теоретически градиент смещён.
3. **Стоимость шага обучения**: target-Q удваивает forward (24 блока из 64
   за шаг — это «бесплатный» сегмент без градиента).
4. **ACT в eval отключён**: на оценке всегда $M_{max}$ сегментов, экономии
   нет; halt-логика работает только в train.
5. **Перенос знаний**: на Sudoku puzzle-эмбеддинг вырожден (1 id), т.е.
   механизм «знания о задаче» здесь почти не используется — в отличие от ARC.
